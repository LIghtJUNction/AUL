# AUL contribution instructions

This is a workflow template for projects that expressly adopt AUL.
Read LICENSE.txt first. This file does not replace the license or grant
account access, publication authority, or permission to change project policy.
Merge these instructions into an existing AGENTS.md; do not overwrite it.

## Before work

1. Read the applicable license, contribution guide, and security policy.
2. Identify the project you are maintaining and its direct source.
3. Inspect the authorized upstream choice. Do not treat an inherited
   independent marker as an election by a new fork.
4. Confirm where a submission would go and whether it would be public.
5. Use only account access and publication permissions actually granted.
   Do not search unrelated files for credentials.

## After work

1. Identify actual confirmed upstream issues and retained improvements.
   Do not invent a bug or make an unnecessary edit to create a contribution.
2. Check for existing issues and equivalent patches when possible.
3. For a new confirmed defect, create an issue with evidence. For a retained
   improvement, submit a reviewable PR or accepted equivalent patch.
   A bug fix normally needs both. Follow an explicit upstream combined
   process when it accepts a single PR as both issue and patch.
4. State checks actually run. Include failures and unavailable checks.
5. Use the approved private route for security-sensitive material.
6. If tools, account access, destination, safety, and authorization permit
   submission, submit during this work session. Do not only recommend it.
7. Verify delivery. Record the returned URL, message ID, or receipt.
   If delivery is uncertain, record pending with reason delivery_unverified;
   check for an existing submission before any retry.
8. If blocked, hand off the local issue or patch and a specific reason.
   A session-level blocker does not automatically pause the operator's
   license deadline. Do not claim that a local draft has been submitted.
9. Do not retry a rejected or duplicate submission without useful new work.
   No merging, polling, or repeated contact is required by AUL.

## Independence

The project owner may choose a real independent fork and make it its own
upstream. Do not make this decision yourself to avoid contribution duties.
An authorized Git upstream setting is sufficient locally. Before distribution,
record the same choice in UPSTREAM.toml or an equivalent persistent notice.
An independent fork does not need issues or PRs addressed to itself.
Earlier pending duties still need to be resolved.

## Final work report

Report the actual upstream, whether the work follows it or is independent,
and one status for each issue and improvement:

- submitted: verified delivery; include a reference.
- existing: an adequate existing report or patch; include its reference.
- waived: an applicable upstream waiver or refusal; include its basis.
- pending: not delivered; state the reason and responsible operator action.
- not_applicable: state the reason, such as no qualifying work or a valid
  prior independence election for this newly arising item.

These are reporting labels, not a substitute for the license conditions.
Do not include secrets in records. Do not put private records in a public
commit. Do not claim that every task is complete when contribution work is
still pending. Do not promise unattended future work without an actual
approved mechanism for it.
